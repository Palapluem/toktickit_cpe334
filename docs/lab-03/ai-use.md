# AI Use and Reflection — Lab 3

## Which agents and models I used

I used Claude Code in a VS Code-based IDE, on Claude Sonnet 5 for the
implementation Issues and Claude Opus 5 for the release audit. As in Lab 2 I
treated the agent as a collaborator rather than an authority: I checked the
contracts, the source, the GitHub state, the test output, the screenshots and
the commit history before accepting a result, and I performed every
peer-review action in the browser myself.

The same phase-template system as Lab 2 carried over — contract review, red,
green, audit, review-response — each naming which documents to read, what to
report, and for the review phases a required `PASS` / `BLOCKED` verdict. Lab 3
added one template that Lab 2 did not have: an **authorization audit** phase,
because this sprint is the first where a wrong answer is a vulnerability
rather than a defect.

Four rows below are those templates, filled in for the Issue or Pull Request
each one ran against; the rest are the judgment prompts used between phases
and at release. Where my actual request was informal or typed in
Thai, it is given here as a clean professional English rendering of the same
request — the same convention Lab 2 used.

## My Reflection

Lab 2 taught me to make prompts name their documents and their forbidden
actions. Lab 3 taught me something narrower: **the most valuable clause in a
prompt is usually the one that tells the agent to attack its own output.**
"Would a stub that refuses everything also pass this test?" exposed red phases
that could not fail. "Do not assume a merged PR reached staging" exposed an
increment that had never reached `lab3-staging`. "Reproduce it before you fix
it" turned a reported hole into a permanent regression test. "Read the AC text,
not the label" found 26 test names citing the wrong criterion. Every suite was
green throughout all four.

The security work sharpened this. In Lab 2 a wrong answer was a bug; in Lab 3
a wrong answer is a hole someone can walk through, and the difference shows in
how little the test suite is worth as evidence on its own. The
cross-tenant status defect passed every test in the file that covered that
endpoint, because every one of those tests used a fixture the caller owned.
The suite was not weak — it was answering a question nobody had asked it.

I also learned that the honest disclosure is cheaper than it looks. I wrote one
module before its tests, disclosed it in the PR with mutation evidence, and the
reviewer engaged with the evidence rather than the lapse. The same held at the
end: the stacked-merge defect came from advice I had given, and writing that
into `reviewer.md` §1.1 took less effort than quietly repairing the branch
would have — and leaves the next person the rule instead of the repair.

What has not changed is where the boundary sits. The agent inspects, drafts and
edits; I decide scope, approve the diff, write the review replies in my own
words, and perform every GitHub action myself. The reviewer's three
behaviour-changing findings this sprint — the CORS fallback, the unscoped
status endpoint, the security signal that never fired — all landed in code an
agent had written and I had accepted. That is the part of the process the
tooling does not do for me.
